# Qwen3.5-0.8B Coding + Instruct Fine-Tuning Project

## Objective

We are going to fine-tune Qwen3.5-0.8B-Base in two phases with the goal of producing a compact model that is strong at:

- Code generation and understanding
- Technical reasoning
- Following instructions
- General English-language assistance

The training will be performed in two distinct phases:

- **Phase 1 — Continued Pre-Training (CPT):** Full-parameter fine-tuning on approximately 1 billion tokens of carefully filtered code, technical documentation, high-quality English web text, and mathematical content.
- **Phase 2 — Instruction Fine-Tuning (SFT):** Train the CPT model on a high-quality instruction/conversation dataset to teach it to behave as an instruction-following assistant.

The immediate task is to design, configure, and prepare the complete Phase 1 pipeline, while keeping the architecture extensible for Phase 2.

## 5. Files and Data to Exclude

### 5.1 Data and Configuration Dumps

Generally exclude:
- `.json`, `.csv`, `.xml`, `.yaml`, `.yml`

unless the file is clearly useful configuration, infrastructure, or CI/CD content.

Examples that may be retained:
- Docker configuration
- CI/CD configuration
- GitHub Actions
- Build configuration
- Meaningful project configuration

Do not apply these exclusions purely based on extension when the file has clear training value.

Exclude lockfiles such as:
- `package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `Cargo.lock`, `poetry.lock`
- Equivalent generated dependency-lock files

### 5.2 Autogenerated / Generated Content

Exclude:
- `*_pb2.py`, `*.pb.go`
- Compiled/generated output, minified code, and build artifacts

Examples:
- `*.min.js`, `*.min.css`
- `/dist/`, `/build/`, `generated/`, `compiled/`

Use robust path and filename detection rather than relying on a single rule.

### 5.3 Low-Value / Obsolete Languages

Do not prioritize or include large quantities of:
- ActionScript, VB6, COBOL, Brainfuck

Also avoid MATLAB/SAS data dumps unless there is a clear reason to retain them.

## 6. Human Language Filtering

The model is intended primarily as an English-based coding and instruction model.

Code comments, docstrings, READMEs, and documentation written in languages other than English should therefore generally be excluded.

Use a language-identification system such as:
- fastText language identification
- Another lightweight and reliable language detector

For documentation/text-heavy samples, retain English samples using:
- English probability > 0.70

However, do not blindly run language identification over every source-code file.

Design a sensible strategy for:
- Source code
- Comments
- Docstrings
- README files
- Documentation
- Mixed-language files

The pipeline should minimize false positives and false negatives.

---

## 7. Low-Quality Code Filtering

Remove obviously low-value samples.

Potential rules include:
- **Low alphanumeric ratio**: Exclude files where fewer than ~50% of characters are alphanumeric when indicative of hex dumps, corrupted files, obfuscated content, ASCII-art-heavy files, binary-like content
- Do not apply this rule blindly to legitimate code where punctuation is naturally frequent
- The filtering system should use multiple signals rather than relying on this metric alone
